## 1. The Mathematical Trapdoor (Asymmetric Relationship)

SSH public key authentication relies on algorithms like **RSA** or **Ed25519** (Elliptic Curve Digital Signature Algorithm). These algorithms are based on mathematical functions that are easy to compute in one direction but virtually impossible to reverse without a specific piece of information.

### The Role Reversal for Signing

|**Key Function**|**Used for Encryption/Decryption**|**Used for Digital Signature (SSH Auth)**|
|---|---|---|
|**Public Key ($P_A$)**|Encrypts a message (only the private key can decrypt it).|**VERIFIES** a signature.|
|**Private Key ($K_A$)**|Decrypts a message (encrypted by the public key).|**CREATES** the signature.|

The key insight is this: **Anything processed using the Private Key can only be successfully reversed/checked using the corresponding Public Key.**

- The client creates the signature ($S$) using its **secret $K_A$**.
    
- The server receives $S$ and uses the **publicly available $P_A$** (from its `authorized_keys` file) to perform the verification.
    

If the verification process (a complex mathematical operation) succeeds, it is an absolute mathematical certainty that the signature $S$ could only have been generated by the **one and only $K_A$** that is linked to $P_A$.

## 2. The Hash Check and Non-Repudiation

Simply signing the challenge ($C$) is not enough. To ensure the signature is specific to the current login attempt and that the data hasn't been tampered with, the SSH server uses a **cryptographic hash** function.

Here is what is signed and verified:

### A. Client Side (Creation of Signature $S$):

1. The SSH client takes the **Challenge ($C$)** received from the server.
    
2. It combines $C$ with a block of data unique to the current SSH session (like the Session ID and other negotiation data).
    
3. The client runs this combined data through a one-way **Hash Function** (like SHA-256 or SHA-512). This produces a small, unique, fixed-length fingerprint (**Hash Value $H$**).
    
4. The client then uses its **Private Key ($K_A$)** to sign (encrypt/process) the Hash Value $H$. This signed result is the **Signature ($S$)**.
    

### B. Server Side (Verification of Signature $S$):

1. The server receives the Signature ($S$) and the same session data used by the client.
    
2. **Decrypt the Hash:** The server uses the client's **Public Key ($P_A$)** to verify/decrypt the Signature ($S$). This process reveals the original **Hash Value ($H$)** that the client signed.
    
3. **Calculate the Hash:** The server independently takes the exact same session data (Challenge $C$ + Session ID) and runs it through the _same_ hash function (e.g., SHA-256). This generates a **New Hash Value ($H'$)**.
    
4. **Compare:** The server compares the two hash values: $H$ (from the client's signature) and $H'$ (the one it just calculated).
    
    - **If $H$ equals $H'$:** The server grants access. This means:
        
        - The sender possesses the private key (because the public key successfully reversed the signature).
            
        - The message data has not been altered in transit (because the hash matches).
            
    - **If they do not match:** The server immediately rejects the connection.
        

This combined method provides both **Authentication** (proof of identity via the key) and **Integrity** (proof that the login attempt wasn't tampered with).
