1. VM sends a TCP packet: src 10.0.2.15:51324, dst 8.8.8.8:443 (HTTPS->443, SSH->22)

2. By default the packed get aimed at the NAT gateway 10.0.2.2, which acts as the router.

3. VirtualBox NAT receives it, creates a mapping, and rewrites the source to the host’s real IP/port, e.g., src 192.0.2.50:45111, dst 8.8.8.8:443.

4. Once the NAT rewrites the source fields, it injects the packet into the host’s own network stack as if a local process had sent it.

5. The packet leaves the host onto the real network with those rewritten addresses.

6. Server replies to src 192.0.2.50:45111. The reply arrives at the host’s NIC. VirtualBox’s NAT engine hooks into the host networking stack: it sees the packet addressed to the host IP/port (e.g., 192.0.2.50:45111), matches it to the translation entry, rewrites the destination to the VM’s 10.0.2.15:51324, and then delivers it onto the VM’s virtual NIC. 

7. So the host receives it, the NAT component rewrites it, and the VM gets the final packet which sees it as coming from 8.8.8.8:443. ^NmfOQHnd

NAT only tracks connections that the VM initiates. When the VM starts an outbound flow, VirtualBox records the 4‑tuple and rewrites the source so replies know where to go. If the host tries to start a new TCP connection toward the VM, there’s no translation entry telling NAT which guest should get it, so the host’s packet is treated as unsolicited and discarded. Outbound (VM→anything) works because it creates the mapping; inbound (host→VM) fails unless you configure port forwarding or another network mode. ^j9n0r23r
